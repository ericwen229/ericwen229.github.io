# 序

我在2022年加入字节跳动API网关团队，负责网关数据面（data plane）的维护。彼时团队刚启动网关融合项目，意图整合字节跳动内部几个网关，开发一个全新的网关取而代之。转眼间四年过去了，团队历经数次组织架构调整，leader换了几任，成员几乎完整换了一遍，但团队的核心使命没变，依旧是网关融合。随着团队的调整，项目的命运也一波三折：初版方案推进了两年，中间改换思路被搁置，再被捡起继续，最终又推倒重来做了新方案，如今新方案依然在推进中。我并非最早加入这个项目的成员，也并非项目中最核心和资深的成员，却成了参与这个项目时间最长的成员之一。古话说：“一鼓作气，再而衰，三而竭。”历经周而复始的冲锋、撤退、再冲锋，目睹团队成员来到又离开，成果被放弃，知识和经验被遗忘，我的内心逐渐从项目中抽离，仿佛我是旁观者而非亲历者。

最近趁着休假重读《人月神话》这本书，发觉半个世纪前的那些经验，在网关融合项目中皆有对应，感慨良多。趁着手上还保留着网关融合的体感和余温，我想把这些感受记录下来，作为对这四年的总结。

# 第二系统

原书对于“第二系统”效应的描述如下：

> 在开发第一个系统时，架构师倾向于精炼和简洁。他知道自己对正在进行的任务不够了解，所以会谨慎、仔细地工作。
>
> 在设计第一个项目时，他会面对不断产生的装饰和润色功能。这些功能都被搁置在一边，作为“下一个”项目的内容。
>
> 第二个系统是设计师们所设计的最危险的系统。
>
> 一种普遍的倾向是过分地设计第二个系统，向系统添加很多修饰功能和想法，它们曾在第一个系统中被小心谨慎地放在次要位置。
>
> ——《人月神话》

网关融合项目最初的名字是网关2.0，意在对网关进行重构升级，正是一个“第二系统”。网关2.0初版方案定型后，团队接手了另一个网关的维护工作，团队使命转向融合两个网关，项目随之更名为网关融合。

同众多的“第二系统”一样，网关融合的初版方案承载了诸多期望。现有的网关经历多年演进，能力趋于完备的同时，技术债也愈发沉重。历史遗留下来不合理的设计、功能和BUG，结成一块儿硬邦邦的混凝土，其中诸多痛点让人无从下手，新想法也难以在其上开展。这时，一个机会出现，告诉我们一切可以从头来过，丢弃所有包袱，纠正所有错误，凝聚全部的经验和智慧，以最正确的方式，设计一个全新的网关，这着实令人难以抗拒。在很多个夜晚，团队全员评审方案到十二点以后，从产品痛点聊到哲学思辨，讨论如何打造一个理想的网关。新网关汇集了诸多愿景：

- 性能：大幅提升性能，降低计算资源成本
- 功能：提供非线性插件编排等进阶功能，支持复杂的编排需求
- 通用：支持在字节私有云/火山公有云/私有化环境等多种环境部署
- 扩展：支持多种网络协议，且易于扩展新的协议
- 融合：融合两个网关，实现技术统一

值得注意的是，初版方案关于融合本身的关注并不多。虽然团队在网关2.0方案的基础之上，针对融合的可行性补充了梳理分析，但在整个叙事逻辑中，融合并非重点要攻克的问题，而是攻克其它问题过后顺理成章的结果——我们将新网关打造得足够好足够完善，能够很好地取代原有网关，便自然实现了融合。因此，初版方案的重心在于如何打造一个足够好足够完善的新网关，其中对性能的重视尤为突出。

网关有充分的理由重视性能，性能既关乎用户体验，也关乎经营成本。在现有网关上，性能的优化空间在持续缩小，提升常常只有几个百分点，团队期望新网关能在性能上取得质的提升。彼时Rust正在公司内部如火如荼地推广，在部分场景下取得了30-50%的性能提升，直接产生巨大的成本收益。在选型阶段，Rust由于其性能和安全性上的优势，成为了极具吸引力的选项。

采用Rust的风险主要在于，现有的数百个网关插件依赖Go公共库生态，全部使用Rust重写会是个艰巨的任务，会严重拖慢项目节奏。因此在可预见的未来内，网关依然需要在Rust程序中加载Go插件，可能会产生一定的性能损失。为此，团队开发了proof of concept版本，在几个测试场景下验证了Rust程序加载Go插件的性能，论证了这个路径的可行性。最终，团队敲定使用Rust开发新网关，命运的齿轮开始转动。

时间快进到两年后，团队经历了一段艰难的时期，刚刚完成组织架构调整。网关融合的使命还在，但Rust网关始终被性能和兼容性问题阻碍，推进得很艰难。Rust程序加载Go插件的开销和复杂程度远超预期，在真实的插件场景下，即使动用了各种优化手段，性能也始终不及预期，部分复杂场景下甚至有劣化。团队在谨慎地评估过后，决定弃用初版的成果，重新做方案设计。大段大段经年累月编写出的文档和代码，它们字里行间流过的经验和设想，以及背后多少个夜晚的讨论，最终被封存和遗忘。

对于初版方案的失败，一种下意识的反思是，我们的proof of concept版本验证不够充分，没能在项目早期预见性能上的问题。对于这种想法，我认为它不算是错误，但未切中关键——我们固然可以把一场战争的失败，归咎于一场关键战役的失败，但不应忽视了是什么样的战略，引入了这场战役，作为左右战争走向的风险点。在我看来，战略上的问题在于，“第二系统”给出的愿景太过美好，使我们想要得太多了。性能、功能、通用、扩展，每一个目标都有其合理性，都没有不带上的理由，但加总起来则太过沉重。项目核心目标原本是融合，仅这一个目标，要达成已然相当艰巨，后文会展开分析原因。但在那些美好愿景面前，融合一定程度上被忽视和低估了。

如果将融合作为绝对的首要目标，一切服务于融合，那么很多决策或许会不同。例如，在技术选型上，为了最小化融合的阻力和风险，应继续沿用Go语言，复用经过充分验证的成熟技术方案、库生态和代码实现；选用最贴近现有网关实现的底层框架，尽可能规避框架层面的兼容性问题。如此一来，很多风险点或许从一开始就不会出现在决策路径上。

下一个章节将分析，为什么即使聚焦于融合，任务依然相当艰巨。

# 复杂度

原书中这样拆解软件工程中的困难所在：

> 我将它们分成根本的（essence）——软件特性中固有的困难，次要的（accident）——出现在目前生产中，但并非那些与生俱来的困难。
>
> 我认为软件开发中困难的部分是规格说明、设计和测试这些概念上的结构，而不是对概念进行表达和对实现逼真程度进行验证。
>
> 软件的复杂度是根本属性，不是次要因素。
>
> ——《人月神话》

对于网关融合项目，复杂度既是目的，也是最大的困难所在。

## 网关的interface与契约

当我们重构一段程序，小到修改一个函数片段，大到替换一个模块，甚至是重写一整个服务，只要这段程序外部可观察行为不发生变化，维持了同外界的契约（所谓“兼容”），那么系统整体运行就可以不受影响。interface即划分了内外部之间的边界，并划定了一个交换信息的窗口，外部到内部为输入，内部到外部为输出。契约建立在interface之上，规定输入输出间的关联。重构要保持兼容，应做到在重构前后，给定任意相同的输入，都能产生相同的输出（实践中还有状态、时序等诸多因素，此处做了大幅简化）。

网关融合也是重构，“融合”的含义在于，代码在重构前有若干份，在重构后只有一份。和所有重构一样，我们需要考虑，网关的interface是什么，输入和输出分别有哪些，输入输出需要满足什么样的契约。而在这方面，网关的interface和契约有两个特点，使得重构工作相当困难。

---
<p/>

其一，网关的interface是贯穿的，契约规定的是整个请求处理链路的行为。

理解一个组件或服务时，我们往往关注它对调用方提供的接口。组件或服务由内而外层层封装，interface建立在最外层，输入是请求，输出是响应，契约规定了什么样的请求对应什么样的响应。

```
                     +-----------+
  request (input) -> |           |
                     | component |
response (output) <- |           |
                     +-----------+
```

网关的特殊性在于，其interface是贯穿的，一端是调用方，另一端是上游服务，中间是整个请求处理链路构成的管道。输入从管道一端进入，输出从另一端离开，两个方向上（请求和响应）均是如此。网关的契约规定的，并非管道某一端（例如，面向调用方这一端）输入和输出之间的关联，而是管道两端之间的关联。换句话说，其规定的是数据在穿越管道的过程中发生了什么变化，包括上行请求如何被处理，以及下行响应如何被转化，这涉及请求处理链路上的各个环节。

此外，请求处理链路上还接入了插件，插件的执行顺序、上下文和读写行为亦是契约的一部分。

```
                     +---------+
  request (input) -> - - - - - - -> request (output)
                     | gateway |
response (output) <- - - - - - - <- request (input)
                     +---------+
                          ^
                          |
                  plugin (input & output)
```

其二，网关的行为由配置和插件共同决定，契约具有高度的差异性。

宏观上，网关是通用组件，可以广泛适用于各个场景，没有固定的输入输出格式。网关对请求和响应的结构长什么样，字段有哪些，类型分别是什么，合法取值是哪些，除了一般意义上的合法性校验，几乎没有固定的约束。特定场景下，用户可以配置特定的schema，但网关本身没有统一的schema。

微观上，网关对请求和响应的处理逻辑有极高的灵活性，场景和场景之间存在显著的差异性。和其他侧重透传转发的组件相比，网关承载的逻辑要更重，定制的自由度更高。这里我举两个例子：

1. 网关支持将HTTP请求转换为RPC请求（响应亦如是），且在基础的映射规则之外，支持通过注解自定义HTTP请求到RPC请求的映射规则，实现不同结构之间的转换。
2. 网关插件对请求和响应有完整的读写能力，能够任意地局部修改或者完整覆写请求和响应。

因而，同样是使用一个网关，不同用户实际依赖的可能是截然不同的行为。实现了同一个功能，不代表已经兼容了这个功能在各种配置和插件组合下的表现。

---
<p/>

由多个交互位点构成的贯穿的interface，再加上行为高度的差异化，意味着网关有着复杂的、千人千面的契约，仅凭梳理枚举难以验证全面，只有逐个真实场景实际验证才可靠。

## “永恒”的技术债

围绕interface建立的契约，构成了网关的本质复杂度。在重构过程中，我们可以更换技术选型来让表述更贴近设计，调整设计来让架构更规整，更换算法来让代码变得更简洁，但那些被外部依赖、因兼容性要求而保留的功能特性，它们的复杂度不会被直接消灭——除非，我们决定移除某些功能特性，但那并非重构的范畴，存在兼容性风险。

我们期望大部分技术债位于契约以外，属于偶然复杂度而非本质复杂度。这也是重构能够消除这部分技术债的前提。它们最好位于那些外界感知不到的地方，从未被承诺，从未被依赖，替换也不破坏兼容。不幸的是，现实情况不是这样的。

原书中提到，实现作为一种spec，体现了过多的内容：

> 实现可能更加过度地规定了外部功能。
>
> 作为一种定义，实现体现了过多的内容：它不但表述系统必须做什么，还声明了自己到底做了些什么。
>
> ——《人月神话》

Law of Leaky Abstraction告诉我们，抽象总是失效的，会透出实现细节：

> All non-trivial abstractions, to some degree, are leaky.
>
> —— Law of Leaky Abstraction

Hyrum's Law告诉我们，被透出的实现细节总会被依赖：

> With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody.
>
> —— Hyrum's Law

网关贯穿的interface，构成了一个巨大的暴露面，将那些看似被隐藏、在用户手册中未被提及和承诺的实现细节，暴露给外部感知。网关覆盖了上万服务，有足够大的用户基数，导致几乎每一个实现细节，都有极大可能在某个不为人所知的角落，被某个不知情的用户依赖，成为实质上契约的一部分，要求我们保持兼容。

要彻底消灭这部分复杂度，我们需要梳理用户实际的使用情况，推动并协助用户改造他们的使用方式，确保无人使用后灰度关闭该功能，最后将功能从代码中彻底移除。而这，远非重构可以达成的目标，因而我们只能轻叹一声，将逻辑原封不动地——或许是以稍微美观一点的方式——移动到新网关，技术债并未直接消失。

## 复杂度的融合

时至今日，我们有三个网关（在新方案中，又有一个网关加入），它们各自演化出相当复杂的功能，此时正待融合。融合工作的具体路径如何设计，是一个重要的问题，但回答这个问题之前，融合工作的最终目标长什么样，值得我们先想一想。理想情况下，我们将打造一个什么样的新网关？它应该具有什么程度的复杂度？它的复杂度和三个现有网关的复杂度之间的关系是什么？

```
+---+   +---+   +---+
|   |   |   |   |   |
| A | + | B | + | C | => ?
|   |   |   |   |   |
+---+   +---+   +---+
```

最优情况是，新网关具有和单个网关相当的复杂度。这意味着三个网关之间有绝佳的兼容性，融合的结果严丝合缝，没有任何冲突，如同历史上从一开始就只有这一个网关。一种极端情况是，三个网关的代码一模一样，可以任意删除其中两个。

```
+---+   +---+   +---+    +---+
|   |   |   |   |   |    |   |
| A | + | B | + | C | => | D |
|   |   |   |   |   |    |   |
+---+   +---+   +---+    +---+
```

这样的设想很美好，但不大可能在融合项目达成。或许有人会产生这样下意识的反问：不都是网关吗？不就是路由、鉴权、限流那几个功能吗？能差异到哪里去？我认为，这样的反问背后，一是对网关的复杂度缺少详细的调研，二是颠倒了举证的方向——对于两个生产级软件，我们应当默认其是复杂和充满差异的，简单才是需要举证的例外。

最差情况是，新网关复杂度是三个网关的简单叠加，根本没有发生实质意义上的融合。例如，只是将三个网关的代码放到一个代码库中存放。

```
+---+   +---+   +---+    +---+---+---+
|   |   |   |   |   |    |   |   |   |
| A | + | B | + | C | => | A | B | C |
|   |   |   |   |   |    |   |   |   |
+---+   +---+   +---+    +---+---+---+
```

这种可能性，主要是作为方案的底线存在——融合工作需要识别三个网关的共性，建立起一个共同的基座，以实现统一演进。代码聚合并不是一种有效的融合。

实际的情况位于两个极端之间，整体复杂度由几个部分构成：

1. 公共逻辑，由三个网关的逻辑去冗取并集得到
2. 差异逻辑，包含三个网关特有的逻辑
3. 融合引入的胶水逻辑

```
+---+   +---+   +---+    +--------+
|   |   |   |   |   |    | common |
| A | + | B | + | C | => +-+-+-+--+
|   |   |   |   |   |    |A|B|C|..|
+---+   +---+   +---+    +-+-+-+--+
```

以此为蓝图，新网关的功能逻辑，可以按照以下方式来规划：

首先，明确区分公共逻辑和差异逻辑，最大限度地保障公共逻辑的概念和设计一致性，将公共逻辑打造成项目中的一块“净土”，作为未来长期演进的基础。

在融合过程中，严格把握公共逻辑和差异逻辑的准入标准——如果功能具备坚实的、值得持续演进的产品价值，能够被纳入公共逻辑的概念体系，就放入公共逻辑，而非硬编码为差异逻辑；相应地，差异逻辑仅存放那些各网关特有、仅为历史兼容保留、未来不再继续演进的功能。严格地隔离公共逻辑和差异逻辑，避免重复的if-else判断散落在公共逻辑中，做好防腐。

最后，在项目的每一个阶段，总是同时考虑多个网关，以敦促我们自己产出足够通用的公共逻辑，来容纳多个网关的差异性。如果先针对某一个网关做重构，完成后再去适配其他网关，很可能无意识地让公共逻辑耦合第一个网关（因为这样做阻力最小），导致后续再适配其他网关时，更容易发生冲突，迫使我们退回去调整设计。又或者，更糟糕的情况是，设计已经定型难以调整，于是我们不得不放弃局部的融合，将它们放入差异逻辑，加重新网关的冗余。

# 人月神话

> 系统编程的进度安排背后的第一个错误的假设是：一切都将运作良好，每一项任务仅花费它所“应该”花费的时间。
>
> 用人月作为衡量一项工作的规模是一个危险和带有欺骗性的神话，它暗示着人员数量和时间是可以相互替换的。
>
> 人数和时间的互换仅仅适用于以下情况：某个任务可以分解给参与人员，并且他们之间不需要相互的交流。这在割小麦或收获棉花的工作中是可行的，而在系统编程中几乎不可能。
>
> 向进度落后的项目中增加人手，只会使进度更加落后。
>
> 同厨师一样，某项任务的计划进度，可能受限于顾客要求的紧迫程度，但紧迫程度无法控制实际的完成情况。……厨师还有其他的选择：他可以把火开大，不过结果常常是无法“挽救”的煎蛋——一面已经焦了，但另一面还是生的。
>
> 项目怎么会延期了整整一年的时间？……一次延期一天。
>
> 慢性进度偏离同样也是士气杀手。
>
> ——《人月神话》

还记得三年前，那是项目初版方案定稿、开完启动会的第二天清晨。虽然团队内部没有事先要求或者约定，但我提前了一小时抵达工位，发现同事也是这样，大家在飞书签名中挂上了focus的状态，积极地投入了项目的开发工作。这种时刻完全不需要言语，就能感受到彼此的决心和士气，真是美好的回忆。

只可惜被低估的复杂度，落在团队上，就是进度灾难。

## 估算不会准确

在前期，团队按部就班开展工作，分模块，拆功能，估时间，写代码。一开始开发进度似乎一切正常，虽然在某些看不见的角落，边界case没有被穷尽，异常处理还留了todo，各个分支也没有完整测试，但里程碑也算有惊无险地如期达成了。只可惜问题没有真正消失，等到上线前验证阶段，每天都有新的问题出现，要停下来分析和修复，上线进度被一再打乱。例会越来越密，周报越来越长，但进度没有越来越快。延期总能被解释，但从未得到解决。

为什么既往的估算方法失灵了？我认为原因有以下几点。

首先，融合的开发事项几乎无法枚举完整。网关本身经过团队多年的迭代，积累了大量的实现细节；通过网关巨大的暴露面，这些实现细节大量地被外部感知，需要保持兼容。在估算工作量时，按照正向实现的思路去估算，或者按照用户手册上的功能去估算，都是不完整的，都无法深入枚举所有的实现细节。而如果要深入，就得把整个代码库细致入微地完整走查一遍，所需的工作量相当庞大，产物的体积可能和代码库在同一个量级。

其次，融合过程并非将已有功能逐个实现一遍，而是持续地将特性集成到新网关中去。对于每个特性，我们需要评估它的影响（是否还在使用），它的历史行为，在新网关应当如何设计，如何同新网关的其余部分整合，整合对现有功能的影响。随着新网关的复杂度持续上升，使用新网关的用户量持续增长，越来越多的行为成为新的既定契约，这个评估和集成的难度会越来越高。

最后，用户使用方式的高度差异性，使我们为稳妥起见，不得不逐个用户（服务）做验证和上线，这个过程具有极大的不确定性。已验证的服务数量用于整体进度估算，准确度很有限，因为在其余未验证的服务中，有多少待解决的问题，解决需要投入多少成本，没有人能给出确定的结论。资源不够可以追加，时间不够可以延期，但不清楚接下来还需要多少资源和时间，会让人觉得项目进度失控。

## 加人不会加速

《人月神话》的核心论点之一，是人员数量和时间无法按比例互换，“人月”这个词语背后的implication不成立。

这一点在网关融合项目中同样应验。团队一度为了加快项目进度，将更多的同学加进项目中，最后甚至全员上阵，但是效率并没有自然而然地取得和人员数量等比例的提升。

首先，如原书中提到的，投入的人力在初期不会立刻转化为生产力，反而会消耗现有人力。加入项目的新同学有上手的过程，需要阅读方案和代码，理解既有的设计实现，熟悉项目的工具和工作流。在这个过程中，新同学需要其他同学的协助，包括对方案和代码进行介绍，私下交流和解答疑问，在代码评审中反复讨论来校正理解。

即使经过培训，所有成员都成为了熟练工，成员之间的协作过程依然具有相当的复杂性，且随着成员数量上升而快速上升。关于协作的复杂性，这里举三个例子：

1. 在分工时，我们通常使用树状结构组织功能模块，并按照这个结构去分工，试图让每个成员都能独立地开展工作，减少彼此之间的制约。但树状结构只是我们切分功能的视角，并非系统内部真实的依赖关系。两个分属不同模块的逻辑，在同一个处理链路上一前一后执行，往往就此构成了隐式的依赖，因此功能模块之间的协作和冲突在所难免，需要沟通协调。
2. 任何的变更，都是在特定scope下进行，需要评估的不仅是这个变更本身的合理性，还有这个变更在更大的scope下是否合理。例如新增某个子模块，需要模块owner来评估其是否遵守了大模块规定的契约，和其他子模块是否协作良好。如果是跨模块的变更，则需要多个模块owner加入review，甚至要项目owner介入，评估系统架构层面的影响。
3. 职能上存在特定的瓶颈点。代码变更需要模块owner或者项目owner来review，准出上线之前需要QA来执行测试和分析结果。处在瓶颈点的同事，带宽上限是固定的，更高的并发加剧了对带宽的抢占，沟通协调又是一项成本。

协作的困难，让我联想到分布式理论下相互牵制的各个命题。单个节点简单有效，但垂直扩容对性能提升有限。为了进一步提升性能，我们引入了多个节点。节点多了需要容错，我们引入了多副本。副本之间需要同步，我们引入了一致性协议。一致性协议的引入，反过来又制约了性能。多个实体间的协作始终是个难题，无论是人还是机器。

## 问题不会收敛

项目的计划制订，取决于我们对于形势走向的判断。网关融合项目中一个关键的判断是，开发阶段的完成度能有多高？用数据来度量便是，开发阶段结束后，遗留到验证阶段的工作量，占比是多少？

一种乐观的主张是，使用细致的梳理和详细的计划，能够将这个占比压得很低，例如不高于10%。相应地，项目计划将具备一种瀑布式的风格，一旦开发阶段结束，预期遗留的问题将会很少，我们可以以此为基础来制订规划。但我们已经知道，枚举不会完整，估算不会准确。宣称开发工作完成了，就如同宣称刚写的代码没有BUG，缺少确切的依据。除非我们将这个验证过程前置，将最终的验证结果作为检验开发完成度的标尺，否则再详细的梳理都谈不上是真凭实据。

在后续验证中，我个人的纯主观体感是，有50%甚至更多的工作量遗留到了验证阶段，在开发阶段我们只完成了一半的开发工作。为了验证这个判断，我对新方案的实施过程做了一个简单的分析，以开发阶段完成的时间点为界，分别统计了时间点前后的代码变更行数，结果显示开发阶段之后产生的变更行数占总体的22%，和体感有着不小的差距。我理解这个差距中有我个人的认知偏差，有代码行数难以体现的单位成本差异（例如，一行代码修复背后要做的分析），还有尚未被发现的遗留工作，有待时间的检验。

还有一种更务实的主张是，认同开发阶段无法穷尽所有细节，验证阶段会有遗留工作要完成，并在计划制订上留有相应的余地。但同时认为，随着问题不断被解决，新网关会日趋完善，问题会逐渐收敛，推进的速度自然会越来越快。对此我抱有疑虑，问题确实在不断被解决，但未必在收敛，这中间差了一个前提——我们验证的样本足够有代表性，能够发现足够广泛的问题。

而实际情况是，新网关的验证和上线，优先选取的都是重要程度低、流量小、场景简单的服务。他们是网关的light user，只用到了网关的基础功能，没有多个功能的组合叠加，没有使用插件或仅使用了基础插件。其中有的用户甚至完全没有意识到自己正在使用网关，使用的一直是默认配置（纯转发）。真正的power user，那些使用了数量繁多的自定义复杂插件，设置了复杂的流量处理策略，请求和响应有着复杂schema转换规则的深度用户，他们的场景还未经验证。

我个人的判断是，随着项目推进，问题数量会下降，但问题的复杂程度解决成本会上升。虽然哪个趋势会成为主导还不明朗，但我相对确信的是，项目的推进不会随着时间的推移自然而然地一马平川，随着项目进入深水区，后续还会有新的难题出现。

# 敢问路在何方

至此，抒发了很多感想，基调显得有些过于悲观了，是时候拉回来一点。网关融合真的是一个“神话”吗？我认为不是，但这样的难题确实是独一份的特殊。

字节跳动坐拥抖音和豆包这样的国民级应用，背后是数万乃至数十万的微服务在浩如烟海的服务器上运行，不乏复杂富有挑战性的问题，例如新区域的机房建设，或是深入业务的资源成本优化。但这些问题往往能有一些行之有效的拆解路径（当然，路径的设计需要相当的智慧、经验和努力），进而被强大的组织动员能力和单兵作战能力解决。

而网关融合项目，是将全公司几乎所有主要业务的接入层深度实践，各个横向团队围绕接入层开发的通用切面，三个团队历经数年、沿不同路径演化出的网关架构，汇聚在由一系列复杂模块紧密关联而成的单体软件中。对于这样一个复杂单体软件，如何保障整体的概念一致性，如何有效地拆解和分工协作，如何兼顾对历史的兼容和面向未来的演进，如何可靠地估算进度和制订计划，是一个软件工程学上的难题，至今没有银弹。相较于常见的任务，它更像一个精巧的数学问题。那种立下军令状，撸起袖子加油干的风格，在它面前是失效的。解决它需要带着充足的耐心，充分理解问题，仔细制订策略，反复摸索前进。

关于如何促成网关融合这件事，以下是我思考得到的一些心得，但没有机会亲身验证了。个人观点，仅供参考。

目标上，绝对聚焦于融合。一切决策服务于融合，技术债融合后再治理（以风险可控为前提），新想法融合后再讨论和演进。

策略上，验证和升级独立开展，维持渐进式升级的同时，将验证工作大幅度前移。尽早录制尽可能多的、具有代表性的业务流量开展回放diff验证，让水面下沉睡的冰山提前暴露出来，以建立更可靠的工作计划和进度预期，提振外部信心和内部士气。持续投入人力优化流程和工具，提升可靠性和易用性，为全体成员提高效率和降低心智负担。

心态上，认清融合不是fancy的短期工作，而是具有重要意义的长期的基础性工作。在这场持久战中，内部要沉得住气，外部也要给予足够的耐心。对于现有网关，也要继续投入资源去识别和解决关键的问题，不可倚赖新网关解决一切问题，避免被长期隐患的突然爆发打得措手不及。

# Why at all?

至此，我们回顾了网关融合项目的历史，拆解了项目的难点所在，分析了过去做错了什么，以及探讨了未来可以怎么做，唯独少了最后一块拼图，是一切的开端。

**为什么要做网关融合？**

乍看这个问题，可能会觉得答案过于显而易见了，不假思索就能想到一堆理由，例如：

- 融合有利于降低维护成本，提升人效
- 融合能够使用户免受N选一的困扰
- 融合有利于网关长期技术演进

但，在我看来，这些理由真正回答的问题是：

**为什么只有一个网关比同时有多个网关要更好？**

理想态为什么好，好在哪里，是显而易见的。但这个问题里，没有我们身处的现实。脚踩在现实，我们应该问出的问题是：

**我们现在已经有多个网关，为什么要融合成一个？**

这可能更让人困惑了——既然理想态是如此，那么我们朝着理想态演进，难道不是理所当然的吗？我觉得未必如此。现实世界从来不是从零开始的，我们面对的，总是已经存在的系统、已经发生的选择，以及由这些选择层层累积而来的现实。现实中很多事物并非是理想态，但依然取得了很好的发展，不一定要倾其所有去纠正，例如：

- Windows操作系统多套历史API并存
- 腾讯系产品微信QQ两套账号体系并存
- 网络基建生态IPv4和IPv6协议并存

而回看团队这四年，理想态的那些收益距离兑现还很遥远，但融合的代价都实实在在地产生了。团队人员几乎悉数流失，网关的已知问题依然存在，团队除了融合没有什么其它方向和成果。

既然融合的代价很高，下一个追问或许是：

**如果不做网关融合，那应该做什么？**

这个问题并非我能解答，且留待团队未来去发挥，前途可期，祝顺利。
