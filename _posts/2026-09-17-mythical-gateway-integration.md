# 序

我于四年前加入字节跳动API网关团队，负责网关data plane的维护。彼时团队启动了网关融合项目，意图整合字节跳动内部几个网关，开发一个全新的网关取而代之。转眼四年过去了，团队历经数次组织架构调整，leader换了几任，团队成员几乎完整换了一遍，但团队的核心使命依旧是网关融合没变。随着团队的调整，项目数次调整思路重新出发，经历和克服了种种困难，至今依然在稳步推进着。

我并非最早加入这个项目的成员，也并非项目中最核心和资深的成员，却成了参与这个项目时间最长的成员之一。老话说：一鼓作气，再而衰，三而竭。历经周而复始的冲锋、撤退、再冲锋，目睹团队成员来到又离开，成果被战略性放弃，知识和经验被遗忘，心态也随之发生了微妙的转变。我的内心逐渐从项目中抽离，在更高处俯瞰着项目的进程，仿佛我是旁观者而非亲历者。

最近趁着休假重读《人月神话》这本书，发觉半世纪前的种种情节，在网关融合项目中皆有对应，感慨良多。趁着手上还保留着网关融合的体感和余温，我想把这些感受整理记录下来。和书中那些取得卓越成就再回首的先驱不同，我未曾做出一番功绩，发表观点不免有些惭愧。但无妨，就交给各位和未来的自己尽情评判吧。

# 第二系统

原书对于“第二系统”效应的描述如下：

> 在开发第一个系统时，架构师倾向于精炼和简洁。他知道自己对正在进行的任务不够了解，所以会谨慎、仔细地工作。
>
> 在设计第一个项目时，他会面对不断产生的装饰和润色功能。这些功能都被搁置在一边，作为“下一个”项目的内容。
>
> 第二个系统是设计师们所设计的最危险的系统。
>
> 一种普遍的倾向是过分地设计第二个系统，向系统添加很多修饰功能和想法，它们曾在第一个系统中被小心谨慎地放在次要位置。

网关融合项目正是发源于一个“第二系统”。事实上，项目最初的名字是网关2.0，意在对网关进行重构升级。网关2.0初版方案定型后，团队接手了另一个网关，决定借契机整合两个网关，项目因此也更名为网关融合。同众多的“第二系统”一样，网关融合的第一次尝试承载了太沉重的期望，最终没能兑现。

在此前，网关经历了漫长的演进过程，能力日渐完备的同时，也背负了太多债务。历史遗留下来合理或不合理的架构设计、代码片段和BUG，结成一块儿硬邦邦的混凝土，痛点一直痛却束手无策，新想法浮现却难以施展。这时，一个机会出现，告诉我们一切可以从头来过，把过去的包袱丢弃，把过去的错误纠正，凝聚整个团队的全部经验和智慧，以最正确的方式，完成全面优于上一代的设计和实现。这样的愿景，着实令人难以抗拒。

在很多个夜晚，团队全员头脑风暴到12点甚至更迟，从现状痛点的梳理演变为产品哲学的思辨，讨论如何打造一个理想的网关。方案设计的进度相比预期要缓慢得多，但鉴于这将是整个团队的终极作品，是一举解决所有问题的“广岛原子弹”，花再多时间打磨细节也是值得的。

在那时，团队为新网关制定下的目标包括但不限于：

- 融合：融合2个网关的现有逻辑
- 兼容：同时向前兼容2个网关
- 性能：性能大幅提升，运行成本大幅降低
- 功能：支持非线性插件编排等进阶能力
- 规范：较为彻底地治理现有的技术债务
- 通用：支持公有云/私有化等环境部署

在最终选型阶段，一个性感的选项进入团队的视野——使用Rust代替Go开发新网关。彼时Rust正在公司内部如火如荼地推广，高性能+安全的卖点十分契合网关场景，部分业务已经成功落地拿到可观的性能收益，生态也正在众人拾柴的热情中一点点补齐。唯一较显著的阻碍在于，现有的上百个网关插件都使用Go开发，使用Rust重写可行性不高，因此网关需要在Rust程序中调用Go插件。团队审慎地评估了这一点，开发了proof of concept版本验证这样做的可行性，随即敲定了使用Rust作为最终技术选型。

时间快进到两年后，团队度过了一段艰难的时期，改朝换代后正在重整旗鼓。网关融合的使命还在，然而项目推进艰难。团队在谨慎评估后，决定弃用先前的全部工作成果，重新设计方案。大段大段经年累月编写出的代码、文档，以及它们字里行间流过的种种设想和教训，最终被封存和遗忘。弃用先前工作成果最主要的原因是，Rust->Go跨语言调用的开销和复杂度远超预期。即使动用了各种优化手段，部分场景下性能仅持平甚至有劣化。

在对此次失败进行反思时，一种下意识的反应是，我们的proof of concept版本验证做得不到位，导致我们没能预见选型上的重大问题，我认为这种想法正确，但太过局限。我们固然可以把战争的失败，归咎于一场关键战役的失败，但忽视了是什么样的战略，引入这场战役作为左右战争走向的风险点，这样的风险是否必要。

战略上的问题在于，我们想要得太多了，融合/兼容/性能/功能/规范/通用，每一个目标孤立地看都合理，都具备可行性，加总起来则太过沉重。仅融合+兼容两个核心目标，要达成已然相当艰巨。如果我们能将全部注意力和资源放在核心目标上，使其它目标最大限度地让位于核心目标，那么某些风险点从一开始就不会出现。例如我们在新方案中决策的，继续使用Go语言和最贴近当前实现的技术框架，不失扩展性前提下仅做合理必要的设计，优先兼容而非治理，一切服务于融合+兼容的目标。

下一个章节将分析，为什么即使聚焦在融合+兼容的目标，任务依然相当艰巨。

# 复杂度

原书中这样拆解软件工程中的困难：

> 我将它们分成根本的（essence）——软件特性中固有的困难，次要的（accident）——出现在目前生产中，但并非那些与生俱来的困难。
>
> 我认为软件开发中困难的部份是规格说明、设计和测试这些概念上的结构，而不是对概念进行表达和对实现逼真程度进行验证。
>
> 软件的复杂度是根本属性，不是次要因素。

对于网关融合项目，复杂度既是目的，也是最大的困难所在。

## 网关interface的特殊性

当我们重构一段程序，小到修改一个函数片段，大到替换一个模块，甚至是重写一整个服务，只要这段程序外部可观察行为不发生变化，保持了同外界的契约，实现了向前兼容，那么系统整体运行就可以不受影响。程序interface划定了内外部之间的边界，交互发生在这个边界上，根据跨越方向的不同，外部到内部为输入，内部到外部为输出，输入决定输出；契约建立在这个边界上，给定特定的输入，程序应产生特定的输出。要实现向前兼容，程序应做到给定任意相同的输入，都能产生相同的输出。

网关融合项目本质上也是重构，“融合”的特殊性仅在于，代码在重构前有若干份，在重构后只有一份。和所有重构一样，我们需要考虑，网关的输入和输出分别是什么。而在这方面，网关有三个区别于一般组件/服务的显著特点，使得其重构工作要困难得多。

其一是，网关的interface是穿透的。

常见的组件/服务，例如Redis和对象存储，对外都是通过特定的端点提供访问，端点接受请求，并返回响应。组件/服务的内部逻辑无论如何层层嵌套，输入输出交互都发生在最外层，内层细节更容易被隐藏。

```
          +---------+
          | service |
          |         |
   req -> =endpoint |
  resp <- |         |
          +---------+
```

对比之下，网关对外提供的并非端点，而是转发代理能力。交互在“两侧”发生——打到inbound侧的请求（输入），预期能够传递到outbound侧（输出）；outbound侧返回的响应（输入），预期能够传递到inbound侧（输出）。输入输出“穿过”了网关的内部，而且存在局部依赖关系（outbound响应依赖outbound请求），使得网关的interface相对复杂，实现兼容的难度更大。

```
inbound        |        outbound
          +---------+
          | gateway |
          |         |
   req -> =--proxy--= -> req
  resp <- |         | <- resp
          +---------+
```

在此基础上，考虑到网关还是诸多业务插件的宿主，将业务插件也纳入网关输入后，interface变得更复杂了。

```
inbound        |        outbound
          +---------+
          | gateway |
          |         |
   req -> =--proxy--= -> req
  resp <- |         | <- resp
          +--^---^--+
             |   |
         plugin plugin
```
